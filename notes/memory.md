| 2026-07-22 | Deployed to Railway via CLI | `railway volume add --service <name> --environment <name>` crashes (CLI bug); using service/environment IDs instead of names works. Also: nginx couldn't resolve `*.railway.internal` even though Railway's API reported the private network as ready — switched the frontend to call the backend's public URL directly instead of debugging that blind. |
| 2026-07-22 | Finished the Railway deploy — both services live, login confirmed working | `railway domain --port N` must match whatever port the app actually listens on (Railway auto-injects its own `PORT`, silently causing a 502 if the two disagree) — hit this on both services. Also `railway up` inconsistently picked its auto-detect builder over the Dockerfile on a later redeploy; committing a `railway.json` pinning `"builder": "DOCKERFILE"` made it deterministic. And: a container restart mid-WhatsApp-session leaves a stale Chromium `SingletonLock` file on the persisted volume that blocks the next launch — clear it on every boot. |
| 2026-07-26 | Connected WhatsApp for real (QR scan succeeded) | A stale/corrupted `wwebjs_auth` session on the volume (left over from earlier crash-loops) made whatsapp-web.js throw an *uncaught* exception ("Failed to add page binding... already exists") that killed the entire Node process, not just the WhatsApp feature — the whole backend went down with it. Fixed by wiping the session dir via `railway ssh` (needed `railway ssh keys add` + a manual `~/.ssh/config` entry disabling host-key checking for `ssh.railway.com` first, since non-interactive SSH can't accept an unknown host key). Real gap still open: WhatsApp failures shouldn't be able to crash the whole app — see follow-up issue. |
| 2026-07-26 | Backend volume got stuck in a broken half-deleted state, losing the DB + WhatsApp session | A `railway volume detach` run while a deletion was still "pending" left the volume permanently orphaned — Railway's dashboard never showed it as a box on the canvas, its own Settings had no Volumes section, and CLI `volume delete` kept silently no-op'ing on it forever. `df -h` was the tell: a real Railway volume shows as its own device (e.g. `/dev/zd...`); ours showed `overlay`, meaning nothing was actually mounted — the data was already gone. Only fix found: delete the whole service (`railway service delete`) and recreate it from scratch with a fresh volume; the ghost volume becomes harmless once unattached, even though it can never itself be deleted. Lesson: never run `volume detach` on a volume mid-deletion — just wait it out, or go straight to recreating the service. |
